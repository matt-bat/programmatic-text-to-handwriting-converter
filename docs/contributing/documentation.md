# Documentation changes

Write for developers and technically curious users. Use plain language, short paragraphs, and concrete terms from the code.

## Style

- Say what the project does before explaining why.
- Prefer direct sentences and familiar words.
- Avoid marketing claims that the code or tests cannot support.
- Explain procedural generation without implying AI, training, or biometric accuracy.
- Keep safety and license statements consistent with the controlling files.
- Do not use private documents, signatures, or handwriting samples in examples.
- Avoid em dashes. Use a period, comma, colon, or parentheses instead.

## Canonical sources

- `README.md` is the public overview and quick start.
- `docs/architecture.md` is the source of truth for system design.
- `SAFETY.md` defines responsible use and the identity-free boundary.
- `LICENSE` is the controlling license text.
- `docs/license-and-safety-rationale.md` explains the intent but does not replace the license.
- `CHANGELOG.md` records release changes.

Update links when the repository name or file layout changes. Use repository-relative links for files in the project.

## Screenshots and media

Use the real application and generic sample text. Keep source text free of personal information. Capture enough of the interface to show the relevant behavior, and include useful alt text wherever the asset is embedded.

Run a link and spelling review before submitting. If a technical claim changed, confirm it against the implementation and tests. Rendering changes should compare new captures with the prior documented generation and explain intentional visual differences, especially for cursive clarity, paper damage, scan simulation, and pagination.
